## 2. 相对原 AC-02 兼容承诺的具体差异

原 AC-02："同 request_id 重试返回同一对象"——按 r3 时代的实现语义，该承诺
**隐含覆盖升级导入的旧请求行**（r3/r4 代码对旧行做通配重放/rev 缺省 1，
F-R5-02 确认这正是缺陷：不同操作被假确认、rev 被编造）。

r6 实现把"重放确认"限定为**意图可完整验证的请求**（本协议 + 已迁移 v2 行）；
旧类别（Phase 1 收据、v1 三列行、残缺 v2 行）一律显式 `request_conflict`，
理由：
1. 旧持久层不含意图内容，"完全相同意图"不可证明（有界调查结论，见 §1）；
2. 元数据变更（tags/pin/folder）不推进 revision，"对象当前看起来一致"不构成
   未变更证明，任何放宽都可能假确认；
3. 原收据仍可查询、旧对象永不因此被改动——丢失的只是"旧行为的自动确认"。

**该差异构成对原 AC-02 兼容承诺的收窄，按合同须由用户对该具体变更作出决策。**

## 3. 决策选项（已裁决：A）

- **选项 A（现状，实现默认）**：接受收窄——旧请求重放一律显式拒绝；
  AC-02 的"同 request_id 重试"承诺限定于可验证意图的请求。
- **选项 B（不推荐）**：对"同对象仍可见"的旧 create/update 收据恢复自动确认
  ——如 §2.2 所述存在元数据假确认风险，需再引入可验证凭证（另立设计）。
- **选项 C**：维持安全拒绝，但把旧行重放的拒绝升级为结构化错误码
  （如 `legacy_request_rejected`）+ UI 提示，与 `request_conflict` 区分（小改动，
  不改变语义）。
